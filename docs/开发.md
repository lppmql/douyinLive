# 开发指南

> 面向新加入项目的开发者。读完本文后你应该能够在本机启动项目、理解代码结构、完成一次完整的开发流程。

## 环境要求

| 依赖 | 最低版本 | 检查命令 |
|------|---------|---------|
| Docker Desktop | 最新稳定版 | `docker --version` |
| Python | 3.10+ | `python3 --version` |
| Node.js | 20+ | `node --version` |
| pnpm | 8+ | `pnpm --version` |
| ffmpeg | 5+ | `ffmpeg -version` |
| Ollama | 0.32+ | `ollama --version` |

> **AI 自动剪辑的字幕依赖**：成片字幕烧录需要带 libass 的 ffmpeg（系统 ffmpeg 一般没有）。
> 系统启动时自动使用项目内 `.runtime/ffmpeg/ffmpeg`（evermeet.cx 静态版，含 libass）；
> 换机器部署时需自行下载放到该路径，或用环境变量 `CLIP_FFMPEG_BIN` 指定带字幕支持的 ffmpeg，
> 否则 AI 自动剪辑会报"找不到支持字幕烧录的 ffmpeg"。
> 可执行 `make doctor` 验证 libass；剪辑任务会在调用 AI 前完成依赖、真实话术、
> 真实回放和 FunASR 检查，前置条件不足时不会产生 AI 选段费用。

> **ASR 单模型线程调优**：`FUNASR_CPU_LIMIT`、`FUNASR_MEMORY_LIMIT`、
> `FUNASR_DECODER_THREAD_NUM`、`FUNASR_MODEL_THREAD_NUM` 和 `FUNASR_IO_THREAD_NUM`
> 位于根 `.env`。仓库默认值兼容低配机器；M1 Pro 32GB 可参考 `4.0 / 3g / 8 / 2 / 2`。
> 修改后需安全停止 ASR，再执行 `docker compose --profile funasr up -d --force-recreate funasr`。

## 首次安装（5 步）

```bash
# 1. 创建本地配置
cp .env.example .env
# 打开 Ollama 应用，创建项目专用本地模型（无需云端 API Key）
./scripts/setup_ollama_model.sh

# 2. 安装后端依赖
cd backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
playwright install chromium
cd ..

# 3. 安装前端依赖
cd frontend
pnpm install
cd ..

# 4. 启动全部服务
./start.sh

# 5. 初始化数据库
cd backend && source .venv/bin/activate && alembic upgrade head
```

启动后访问：
- 前端：http://localhost:9527
- API 文档：http://localhost:8000/docs
- 健康检查：http://localhost:8000/health

## 日常开发命令

日常启动按系统使用仓库根目录入口：macOS/Linux 执行 `./start.sh`，Windows 原生 PowerShell 7 执行 `pwsh -File .\start.ps1 standard`。检查和维护命令封装在 Makefile 中，从项目根目录执行：

```bash
make doctor       # 检查环境是否正常（依赖、容器、磁盘、端口）
make check-docs   # 普通文档等低风险改动：差异格式检查
make check        # 高风险改动：完整检查（含覆盖率、构建、迁移、Docker）
make test         # 全量后端测试 + 前端类型检查，不默认统计覆盖率
make test-backend # 只跑后端 pytest，不默认统计覆盖率
make test-backend-cov # 全量后端 pytest + 45% 覆盖率门槛
make test-frontend # 只跑前端类型检查
make lint         # 后端 Ruff + 前端 ESLint、Oxlint
make build        # 前端生产构建
make migrate      # 数据库升级到最新版本
```

## 开发流程（每次改代码都按这个来）

### 1. 开始前

本项目现在统一采用 **直接在 `main` 开发**。

大白话理解：
- `main` 就是唯一工作主线，不再为日常任务额外创建功能分支。
- 这样命令最少、最容易理解，但也要求提交前检查更严格。
- 每次动手前先确认工作区干净，别把上一次没处理完的文件混进新提交。

```bash
git switch main                # 回到主分支
git status                     # 确认没有无关脏文件
git pull origin main          # 拉最新代码
make doctor                   # 确认环境正常
```

如果 `git status` 看到陌生文件，不要直接覆盖或删除。先问清楚它们是什么；必要时用 `git stash push -u -m "说明文字"` 临时备份。

### 2. 修改代码

**一次只改一个明确目标。** 比如"给首页加导出按钮"是一个目标，"同时优化导出和修复采集 bug"是两个目标——应该分两次提交。

**后端改动：**

- API 接口必须写 `response_model`（已有 40+ 接口这样做）
- 新接口/改字段 → 同步更新 `schemas/` 下的 Pydantic 模型
- 数据库结构变更 → 必须走 Alembic（见下方）
- 新业务逻辑放 `services/`，不要在 `api/` 里写复杂逻辑

**前端改动：**

- 页面组件放 `views/`，可复用组件抽到 `components/`
- API 调用放 `service/api/douyin.ts`
- TypeScript 类型放 `typings/api/douyin.d.ts`
- **禁止手写后端已有的响应类型**——改后端 Schema 后执行 `pnpm gen-api` 自动生成

### 3. 后端 Schema 改了之后（必须做）

```bash
cd frontend
pnpm gen-api         # 从 OpenAPI 重新生成 TypeScript 类型
pnpm typecheck       # 确保前端类型与后端一致
```

**前后端类型不同步会导致线上运行时崩溃。** CI 会拦截这种情况，但本地先跑一遍更快。

### 4. 数据库改了之后（必须做）

```bash
# 1. 修改 ORM 模型（backend/app/models/）
# 2. 生成迁移
cd backend
source .venv/bin/activate
alembic revision --autogenerate -m "描述你的改动"

# 3. 人工检查生成的迁移文件（backend/alembic/versions/）
#    确保它只包含你想要的变更，没有误删字段或表

# 4. 本地测试升级 + 降级 + 再升级
alembic upgrade head
alembic downgrade -1
alembic upgrade head

# 5. 确认没问题后提交迁移文件
```

**禁止：**
- 手动直接改数据库表
- 修改已经合并到 main 的迁移文件
- 用 `create_all()` 替代迁移
- 删除字段前不做数据备份

### 5. 提交前检查

按改动风险选择一档，不要每次把所有命令重复跑一遍：

| 改动范围 | 必要检查 |
|---|---|
| 低风险：普通说明文档、注释、提示文案、配置示例的说明文字 | `make check-docs` + 必要格式检查 |
| 中风险：单个后端模块，不改公共接口或数据结构 | 相关 pytest（不统计全局覆盖率）+ Ruff |
| 中风险：单个前端模块，不改公共交互流程 | 完整类型检查 + 相关 Lint，不默认构建 |
| 高风险：迁移、安全、Docker、启动脚本、依赖、构建配置、公共接口、跨模块/前后端联动、CI/检查入口 | `make check` |

中风险快速入口示例（从项目根目录运行，按实际改动替换文件路径）：

```bash
# 后端路径相对于 backend；TESTS 必填，FILES 可省略（默认 Ruff 检查 app/）
make check-backend TESTS="tests/test_local_llm_client.py" FILES="app/services/ai/llm_client.py"

# 前端路径相对于 frontend；类型检查仍覆盖整个前端
make check-frontend FILES="src/views/home/index.vue"
```

覆盖率就是“测试执行过多少业务代码”。只测试一个模块时，不应要求覆盖整个后端；因此直接执行 pytest 和快速后端入口不再统计全局覆盖率。高风险 `make check` 和代码类 CI 继续使用 45% 门槛，没有降低标准。完整 `make check` 还包含前后端 Lint、类型检查、生产构建、Alembic 和 Docker 配置校验。

推送后，GitHub Actions 先对整次推送/PR 的差异做轻量分类和空白检查。只有根目录 `README.md`、`CHANGELOG.md`、`AGENTS.md` 以及 `docs/` 下的 Markdown 说明文档，才跳过依赖安装、数据库和构建等重任务。`docs/行业知识/` 会被知识库与 ASR 热词读取，属于业务数据，始终保留完整 CI。代码、配置、混合改动和无法确认的范围也保留完整 CI；源码里的注释或文案不能仅凭路径识别，CI 同样保守执行全量。

API 类型一致性检查继续保留，合并到后端 CI 任务复用 Python 依赖；生成器版本与前端锁文件一致，并由回归测试保护。若升级 `openapi-typescript`，应同时更新 CI 中的固定版本。

本地检查通过后，代码改动仍需 `code-reviewer` 审查。`unit-tester` 只补缺失检查，不复跑已有结果；修复审查问题后只重跑受影响的项目。真实模型、长音频、浏览器和采集验收仅在相关功能变化时执行，不作为普通改动的默认步骤。满足所选风险级别的必要检查后才能提交。

### 6. 提交规范

```bash
git add <文件>
git commit -m "类型: 日期 简短描述"
```

类型用这些：
- `feat:` 新功能
- `fix:` 修复 bug
- `perf:` 性能优化
- `refactor:` 重构（不改变功能）
- `docs:` 文档
- `chore:` 工具链、配置

示例：`feat: 2026-07-21 首页新增导出按钮`

### 7. 更新 CHANGELOG

在 `CHANGELOG.md` 顶部对应日期下添加变更记录。按 Added / Changed / Fixed / Removed 分类。

如果改动了架构决策（比如换了一个关键技术方案），在 `docs/adr/` 新增 ADR。

### 8. 推送

```bash
git push origin main
```

推送前再看一眼：

```bash
git status
git log --oneline --max-count=3
```

确认只有本次明确改动后再推送。`main` 是正式主线，不能把半成品、测试产物、密钥文件一起推上去。

## 代码红线

这些不是硬规定，但每次评审都会检查：

```
Python 文件超过 500 行 → 评估拆分
Vue 文件超过 400 行    → 评估拆分
单个函数超过 80 行     → 优先拆分
函数参数超过 6 个      → 考虑用对象
```

## 职责分层（后端）

```
api.py         → 只处理请求参数和返回响应
schemas.py     → 只定义接口数据结构
service.py     → 只处理业务逻辑
repository.py  → 只操作数据库（未来引入）
models.py      → 只定义 ORM 模型
```

目前 services 层部分文件直接写 SQLAlchemy 查询。长期方向是引入 repository 层，但这不是当前最紧急的事。

**一个 service 不应该同时做：** Playwright + MySQL + Redis + AI + ffmpeg。这些外部能力应该通过 `infrastructure/` 或独立 service 调用。

## 测试分层

```
单元测试   → 纯业务逻辑（线索判断、指标计算、AI 输出解析）
集成测试   → API + MySQL、任务状态流转、Alembic 迁移
核心链路   → 创建模拟场次 → AI 复盘 → 首页统计（端到端）
```

## 环境变量规范

```
根 .env       → 后端、Docker、密钥（不进入浏览器）
frontend/.env → 只放 VITE_* 前缀的公共配置
```

每个变量应标注：用途、默认值、是否必填、是否敏感、修改后需不需要重启。

## 任务状态规范

所有后台任务（采集、ASR、AI 分析）使用 `core/status.py` 中定义的 `TaskStatus` 枚举：

```
pending   → 已创建，等待执行
queued    → 已入队（ASR 专用）
running   → 执行中
completed → 成功
failed    → 失败
cancelled → 已取消
```

> 业务模块（采集/ASR/场次）可使用"领域状态"细化，前端任务中心统一使用以上展示状态。详见 `core/status.py`。

# ADR 0026 — 客资自动归属：从精确匹配到四级匹配

**日期**：2026-07-27
**状态**：✅ 已实施
**关联**：[[0025-客资同步卡片与源编号契约]]

---

## 背景

kezi.lpp6.com 首次同步导入 1592 条客资后，**全部 1592 条都是"待归属"状态**。原因有两个：

### 问题 1：主播名对不上

| kezi 客资服务（短名） | 直播场次（完整标题） | 旧匹配逻辑 |
|----------------------|---------------------|-----------|
| 丹丹 | 丹姐谈零食店天准 | `==` 不匹配 |
| 大全 | 大全谈开店天准 | `==` 不匹配 |
| 飞哥 | 飞哥洢洢聊零食店 | `==` 不匹配 |
| 民哥 | 民哥聊零食店 | `==` 不匹配 |
| 文豪 | 文豪聊零食店天准 | `==` 不匹配 |

旧代码用的是精确相等（`anchor_name == item.anchor`），但 kezi 保存的是用户填写的短名/昵称，直播场次保存的是抖音直播间完整标题。

### 问题 2：时间窗太严格

旧代码要求 `开播时间 ≤ 客资时间 ≤ 下播时间`，没有缓冲。但实际情况：
- 用户在开播前几分钟就进了主页留资
- 用户在下播后看回放/逛主页时留资
- 留资表单提交可能延迟几十秒

### 问题 3：换号播 / 当天没播

主播可能用多个号轮播（比如先用大号播，再换小号播），或者当天休息没播。这种情况下当天找不到场次，但主播在其他日期有直播记录。应该匹配到最近的历史场次。

## 决策

采用**四级匹配**策略：

### 第 1 级：主播名模糊匹配 + 时间窗匹配（优先）

**名字匹配分两层**，避免首字匹配太宽造成误判：

1. 精确匹配 + 包含匹配（优先）：`==` 或 `LIKE %锚名%`
2. 首字匹配（兜底）：仅在第 1 层无结果时才启用（`LIKE 首字%`）

**时间窗加缓冲**：
- 开播前 30 分钟
- 下播后 60 分钟

结果：
- 恰好 1 个场次匹配 → ✅ 直接归属
- 0 个 → 进入第 2 级
- 多个 → `_pick_closest_session` 去重（优先选客资在直播时段内的，其次选最近场次）

### 第 2 级：同一天兜底

如果时间窗匹配不上，但客资和直播是同一天，且当天只有 1 场直播 → 兜底归属。

多场次同一天 → 进入第 3 级。

### 第 3 级：同天多场次，就近匹配（间隙匹配）

同一天有多场直播但客资时间落在场次之间的空隙 → 找离客资时间最近的一场。
- 优先找"刚下播的"（end_time < lead_time 且时间差最小）
- 其次找"马上要播的"（start_time > lead_time 且时间差最小）

备注：「下播后留资（自动匹配到最近场次）」

### 第 4 级：当天没直播，按主播不限日期就近匹配

当天完全没有该主播的直播记录 → 在所有历史场次中找最近的一场。
这可能意味着主播当天换号播了，或者当天休息但客资是从历史回放来的。

备注：「当天无直播记录 / 换号播的」

### 为什么"首字匹配"要分层而不是一次全查？

如果把精确/包含/首字全部放在一个 `OR` 查询里，像测试用例中的"主播甲"会通过首字"主"误匹配到"主播乙"。分层后，只有精确+包含没结果时才会启用首字匹配。

## 实施效果（最终）

| 匹配级别 | 数量 | 占比 | 备注 |
|----------|------|------|------|
| 第 1 级（时间窗） | 1427 | 89.6% | 无备注（高置信） |
| 第 2 级（同天兜底） | 0 | 0% | — |
| 第 3 级（间隙就近） | 41 | 2.6% | 「下播后留资」 |
| 第 4 级（当天没播） | 124 | 7.8% | 「当天无直播记录 / 换号播的」 |
| 待归属 | **0** | 0% | 🎉 |
| **总计** | **1592** | 100% | |

### 关键修复：多窗口去重

初版在 Level 1 多个时间窗匹配时直接返回 None（"证据不足"），导致 175 条客资因为缓冲窗口重叠而无法匹配。后改为用 `_pick_closest_session` 去重：
- 优先选客资落在直播时段内（不含缓冲）的场次
- 多个都在时段内时选距结束最近的
- 都不在时段内时选最近场次

这个改动让 175 条"证据不足"的客资全部成功归属。

## 技术细节

### 改动文件

| 文件 | 改动 |
|------|------|
| `backend/app/services/leads/kezi_sync.py` | `match_live_session` 新增第 4 级；`_save_item` / `rematch_pending_leads` 处理新备注 |
| `backend/app/api/v1/leads.py` | `POST /sync` 新增 `?rematch=true` 参数 |
| `backend/app/schemas/leads.py` | `LeadSyncResponse` 新增可选 `rematch` 字段 |

### 重匹配入口

```bash
curl -X POST "http://localhost:8000/api/v1/leads/sync?rematch=true"
```

传 `rematch=true` 会先把所有 `pending` 客资重跑匹配逻辑，再执行正常的增量同步。

## 踩坑记录

1. **中文引号导致 SyntaxError**：Edit 工具把 `"""` 转成了 `"""`（U+201C/U+201D），Python 解析失败。用 Python 脚本全局替换解决。
2. **首字匹配太宽**：第一版把精确/包含/首字放在一个 `or_()` 里，测试用例中"主播甲"的首字"主"误匹配了"主播乙"。改为分层查询后修复。
3. **同一天多场次**：不能无脑归到"同一天第一场"或"同一天最后一场"，因为中间场次的客资会被错误归属。用就近匹配（`_pick_closest_session`）解决。
4. **rematch 刷新备注**：`rematch_pending_leads` 对仍无法匹配的客资也更新备注，区分"当天没播"（`_query_candidates` 有结果）和"换号播的"（`_query_candidates` 无结果）。

## 后续优化方向

- 如果有更多信号（如私信内容时间戳、用户活跃时段），可以进一步区分同一天多场次的情况
- 可以在前端加一个"批量归属"功能，把同一主播同一天的所有待归属客资一键指定到某一场

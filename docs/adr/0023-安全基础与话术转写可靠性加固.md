# ADR 0023：安全基础与话术转写可靠性加固

**日期**：2026-07-27
**状态**：已实施

## 背景

本轮按已经确认的路线推进第一阶段：

1. 先完成方案 A 的安全基础，避免业务接口、媒体地址、短信验证码和内部刷新接口被越权调用。
2. 同步修复话术转写，保留实时识别能力，并把长直播改成每 2 分钟一个可恢复的小分片。
3. 为下一阶段的留资业务闭环准备一个可独立部署的安全版客资服务，但在远端服务完成鉴权升级前，不拉取真实客户隐私数据。

真实数据库排查发现两类转写故障：

- 历史任务在直播时长被修正后仍复用旧分片计划，导致 Worker 继续处理超过真实结束时间的分片。
- 直播中的任务可能创建“从 0 秒一直读到流结束”的无限分片，ffmpeg 长时间不退出，心跳也无法及时更新。

## 决策

### 1. 采用三档角色和默认拒绝

角色统一为：

- `R_VIEWER`：只能查看。
- `R_USER`：可以执行业务写操作，但不能删除数据或管理用户。
- `R_SUPER`：拥有全部系统管理权限。

历史 `R_ADMIN` 在权限判断时兼容为 `R_SUPER`，避免升级后已有管理员突然失去权限。没有明确放行的业务路径按“默认拒绝”处理。

### 2. 媒体和内部刷新不再公开

- 视频流、回放和 WebSocket 必须持有有效登录身份。
- 浏览器原生视频标签继续使用短时 `HttpOnly` 媒体 Cookie。`HttpOnly` 的大白话含义是：网页脚本读不到这个凭证，降低被恶意脚本偷走的风险。
- ASR Worker 刷新直播流时使用独立内部令牌，并用恒定时间算法校验，避免把普通用户登录令牌写进后台进程。
- 日志不记录直播流完整地址、令牌、手机号和短信验证码。

### 3. 删除默认弱口令，改为一次性初始化

新数据库迁移不再自动写入固定的 `admin/Admin123456` 和 `user/User123456`。

只有用户表为空时，系统才允许使用根目录 `.env` 中的初始化管理员账号和至少 15 位密码创建首个超级管理员。已有数据库用户完全保留，不重置密码。

### 4. 短信验证码采用随机数、摘要和原子消费

- 验证码使用安全随机数生成，不使用普通伪随机函数。
- Redis 只保存验证码的 HMAC 摘要，不保存明文。
- 校验成功时使用 Redis Lua 脚本“一次比较、一次删除”，防止同一个验证码被并发重复使用。
- 按 IP、手机号、登录账号分别限流。
- 开发环境也不再把真实验证码放进接口响应。

### 5. 话术转写采用 2 分钟滚动分片

- 实时直播：始终只处理一个有限的 120 秒窗口，完成后再追加下一个窗口。
- 已结束直播：按真实时长生成 120 秒分片，最后一片自动缩短。
- 时长修正后重新核对旧分片：保留已有真实话术；没有内容且超出真实结束时间的分片标记为 `skipped`，不再送给 ffmpeg。
- Worker 处理分片期间每 30 秒独立更新任务和分片心跳。
- Worker 重启造成的中断不消耗正常业务重试次数。
- 每个分片都有硬超时，避免底层进程永久占用资源。
- 离线回放在分片完成点和 FunASR 模型等待点都会检查实时队列；有新直播时保存断点并礼让，避免单 Worker 被历史长任务或模型恢复等待占满。
- 单并发被离线任务占满时，仍允许一个真实直播任务进入等待队列，确保 Worker 能实际看见它并在分片边界礼让。
- ffmpeg 一个音频帧都没有输出时立即让当前分片失败重试，不再把整场空流误记成几十个“已完成”分片。
- FunASR WebSocket 中途断开会让当前分片失败重试，不会把不完整结果标为完成；任务领取与模型连接均固定单并发。即使离线任务占着唯一槽位，Worker 仍会先发现实时任务并让它进入队列，再在两分钟边界完成礼让。
- 旧任务的已完成分片边界永不改写；例如旧 300 秒文字分片升级到 120 秒配置时，只从 300 秒以后补建，避免话术重叠。
- FunASR 崩溃重启后按环境配置最长等待 15 分钟加载 1.6GB 模型，启动脚本与 Worker 使用同一配置，不再写死 300 秒。

### 6. 客资服务先提供安全部署包，不直接读取现网隐私

`deploy/kezi-service/` 保留原服务的三个接口：

- `/api/kezi`
- `/api/douyinhao`
- `/api/stats`

部署包新增读写分离的 Bearer Token、限流、严格字段类型和长度校验、隐私日志保护、环境变量配置和仅监听本机回环地址；同时保留原来的 `received`、`filters` 响应字段。现网 `https://kezi.lpp6.com` 当前尚未提供鉴权，因此本阶段不把它直接接入主系统，也不读取真实客资。

Bearer Token 的大白话含义是：调用接口时必须同时带上一串服务器认可的通行证。

## 真实验收证据

- 后端全量测试：271 项通过，覆盖率 51.05%。
- 前端类型检查和生产构建通过。
- 未登录访问媒体回放和流刷新接口均返回 401。
- 真实采集启动后成功恢复项目保存的 Cookie、StorageState 和浏览器指纹，并继续采集真实直播快照。
- 最终运行态实时 ASR 任务 `#331` 已连续完成 3 个 120 秒分片，第 4 个分片处理中；任务和分片心跳持续更新，且同时只有 1 个 ASR 任务处于 `processing`。
- 历史任务 `#323` 最终保留 45 个已完成分片，并安全跳过 14 个越界且没有文字的分片；已有话术没有被删除。
- 真实运行进一步确认历史流没有输出音频时会被识别为技术失败；不再把“没有读到音频”误判为“成功但没有话术”。
- 真实 FunASR 容器曾自动重启 4 次且未发生 OOM，但低内存环境重新加载模型超过 5 分钟；等待上限已按实测调整为 15 分钟。

## 影响与后续

- 当前完成的是“A 的安全基础 + 话术转写修复”。
- 下一阶段 B 先把安全版客资服务部署到原服务器，再实现增量同步、去重、来源追踪和留资漏斗。
- 再下一阶段 C 拆分大模块、统一领域模型和依赖边界。
- 现有业务功能均保留；只有原本不安全的匿名访问和弱口令初始化方式被收紧。

## 替代方案

### 方案 B：关闭实时转写，只在下播后离线处理

优点是实现简单、资源更稳定；缺点是直播中看不到话术进度，不符合本项目运营复盘的实时需求，因此未采用。

### 方案 C：整场直播只创建一个无限分片

优点是分片数量少；缺点是无法可靠心跳、暂停、超时和断点续传，也是本次故障的直接来源，因此未采用。

### 方案 D：直接调用当前无鉴权客资服务

接入速度快，但任何知道地址的人都可能读取客户隐私，不满足安全基础要求，因此必须等服务端鉴权部署完成后再接入。

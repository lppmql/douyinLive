# ADR 0026 — 客资自动归属：从精确匹配到两级模糊匹配

**日期**：2026-07-27
**状态**：✅ 已实施
**关联**：[[0025-客资同步卡片与源编号契约]]

---

## 背景

kezi.lpp6.com 首次同步导入 1592 条客资后，**全部 1592 条都是"待归属"状态**。原因有两个：

### 问题 1：主播名对不上

| kezi 客资服务（短名） | 直播场次（完整标题） | 旧匹配逻辑 |
|----------------------|---------------------|-----------|
| 丹丹 | 丹姐谈零食店天准 | `==` 不匹配 |
| 大全 | 大全谈开店天准 | `==` 不匹配 |
| 飞哥 | 飞哥洢洢聊零食店 | `==` 不匹配 |
| 民哥 | 民哥聊零食店 | `==` 不匹配 |
| 文豪 | 文豪聊零食店天准 | `==` 不匹配 |

旧代码用的是精确相等（`anchor_name == item.anchor`），但 kezi 保存的是用户填写的短名/昵称，直播场次保存的是抖音直播间完整标题。

### 问题 2：时间窗太严格

旧代码要求 `开播时间 ≤ 客资时间 ≤ 下播时间`，没有缓冲。但实际情况：
- 用户在开播前几分钟就进了主页留资
- 用户在下播后看回放/逛主页时留资
- 留资表单提交可能延迟几十秒

## 决策

采用**两级匹配**策略，只改 `match_live_session()` 一个函数：

### 第 1 级：主播名模糊匹配 + 时间窗匹配（优先）

**名字匹配分两层**，避免首字匹配太宽造成误判：

1. 精确匹配 + 包含匹配（优先）：`==` 或 `LIKE %锚名%`
2. 首字匹配（兜底）：仅在第 1 层无结果时才启用（`LIKE 首字%`）

**时间窗加缓冲**：
- 开播前 30 分钟
- 下播后 60 分钟

结果：
- 恰好 1 个场次匹配 → ✅ 直接归属
- 0 个 → 进入第 2 级
- 多个 → 待归属（不瞎猜）

### 第 2 级：同一天兜底

如果时间窗匹配不上，但客资和直播是同一天，且当天只有 1 场直播 → 兜底归属。

多场次同一天 → 待归属。

### 为什么"首字匹配"要分层而不是一次全查？

如果把精确/包含/首字全部放在一个 `OR` 查询里，像测试用例中的"主播甲"会通过首字"主"误匹配到"主播乙"。分层后，只有精确+包含没结果时才会启用首字匹配。

## 实施效果

| 指标 | 修改前 | 修改后 |
|------|--------|--------|
| 自动归属 | 0 条 | **1252 条**（78.6%） |
| 待归属 | 1592 条 | 340 条（21.4%） |
| 归属场次 | 0 | 106 场 |

### 340 条仍待归属的原因

都是**同一天同一主播有多场直播**（3~4 场/天），客资时间落在两场之间的空隙，系统无法确定属于哪一场。这是正确的保守行为。

这些客资可以通过人工归属界面手动指定场次。

## 技术细节

### 改动文件

| 文件 | 改动 |
|------|------|
| `backend/app/services/leads/kezi_sync.py` | 重写 `match_live_session`，新增 `_query_candidates`、`_get_session_end_time`、`rematch_pending_leads` |
| `backend/app/api/v1/leads.py` | `POST /sync` 新增 `?rematch=true` 参数 |
| `backend/app/schemas/leads.py` | `LeadSyncResponse` 新增可选 `rematch` 字段 |

### 重匹配入口

```bash
curl -X POST "http://localhost:8000/api/v1/leads/sync?rematch=true"
```

传 `rematch=true` 会先把所有 `pending` 客资重跑匹配逻辑，再执行正常的增量同步。

## 踩坑记录

1. **中文引号导致 SyntaxError**：Edit 工具把 `"""` 转成了 `"""`（U+201C/U+201D），Python 解析失败。用 Python 脚本全局替换解决。
2. **首字匹配太宽**：第一版把精确/包含/首字放在一个 `or_()` 里，测试用例中"主播甲"的首字"主"误匹配了"主播乙"。改为分层查询后修复。
3. **同一天多场次**：不能无脑归到"同一天第一场"或"同一天最后一场"，因为中间场次的客资会被错误归属。保留待归属是正确的。

## 后续优化方向

- 如果有更多信号（如私信内容时间戳、用户活跃时段），可以进一步区分同一天多场次的情况
- 可以在前端加一个"批量归属"功能，把同一主播同一天的所有待归属客资一键指定到某一场

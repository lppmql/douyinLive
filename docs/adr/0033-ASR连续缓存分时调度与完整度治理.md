# ADR 0033：ASR 连续缓存、分时调度与完整度治理

- 日期：2026-07-30
- 状态：已采纳

## 背景

真实任务显示，直播初稿按实时速度发送音频，一场长直播会持续占用唯一的
FunASR 模型；旧的离线终稿只能一直等待。直播下播瞬间，最后一个实时分片还
可能读取到已失效的 m3u8（404），导致前面已经成功的 18 个分片被整场标记失败。

本机只有 8GB 内存，FunASR 容器已经接近自身内存上限，因此不能安全启动第二套
模型。系统需要在单模型条件下同时保证直播不漏音、最新下播终稿及时推进，并能
明确判断话术是否覆盖完整。

## 备选方案

### 方案 A：继续直播独占，等待下播再处理终稿

改动最小，但离线终稿会被长直播阻塞，直播末尾仍可能因流失效失败。

### 方案 B：启动第二套 FunASR

两个任务可以物理并行，但当前机器内存不足，容易让两个模型一起崩溃。

### 方案 C：单模型双逻辑队列 + 独立音频缓存

ffmpeg 连续保存真实直播 PCM，FunASR 按直播与最新终稿分时消费缓存；不增加模型
内存，同时不会因终稿占用识别器而漏掉直播声音。

## 最终决策

采用方案 C：

1. 每场直播启动独立 ffmpeg，把 16kHz、单声道、16 位真实 PCM 连续写入
   `data/asr-buffer`。
2. 单个 FunASR 物理连接按“3 个直播分片：1 个最新下播终稿分片”公平调度，
   两个逻辑任务可以准备，但绝不同时连接模型。
3. 最新下播终稿优先于较旧终稿；旧任务只在两分钟分片边界礼让，已完成分片保留。
4. 在线初稿以每 50ms 发送 60ms 音频帧，约 1.2 倍速追赶缓存；在线收尾等待从
   固定 15 秒缩短为 3 秒，离线终稿仍保留 15 秒。
5. 实时任务最后一片遇到下播 404、无音频或缓存结束时，保留成功初稿并创建独立
   离线终稿，不再把整场标为失败。
6. 完整度以“已完成音频分片覆盖真实直播时长”计算，不把沉默误判为缺失；离线
   失败会只重跑缺失区间，最多自动续接 3 轮。
7. 语速按有效字符数除以合并后的有话术时间计算。离线终稿完成前明确标记为
   “直播初稿估算”，未知真实时长时不伪造覆盖率。

## 配置与容量

- `ASR_LIVE_CHUNK_QUOTA=3`：直播连续处理分片数。
- `ASR_AUDIO_BUFFER_RETENTION_HOURS=24`：PCM 保留时间。
- `ASR_AUDIO_BUFFER_MAX_GB=2`：缓存总容量上限。
- `ASR_ONLINE_FRAME_INTERVAL_SECONDS=0.05`：在线帧发送间隔。
- `ASR_ONLINE_RESULT_TIMEOUT_SECONDS=3`：在线结果收尾等待。
- `ASR_COMPLETENESS_REPAIR_ROUNDS=3`：真实时长继续修正时的缺口追加硬上限。

PCM 约占 115.2MB/小时，2GB 上限可保存约 17 小时。运行中和待终稿复用的文件
会计入总量但不会被删除；每个 ffmpeg 进程同时使用 `-fs` 硬限制自己的剩余额度。
额度不足一个完整分片时不启动新缓存，回退为原有直播流直读。超期或超容量时从
不再被任务引用的最旧文件开始清理。缓存目录已由项目现有 `data/` 规则忽略，
不进入 Git。

## 影响范围

- ASR Worker、FunASR 客户端、资源策略和运行配置。
- 直播详情接口新增 `transcript_quality`。
- 直播详情页新增话术覆盖状态和“字/分钟”语速卡片。
- 不新增数据库表，不修改已有话术、复盘、客资或 DataEase 功能。

## 验收方式

1. 直播与最新下播终稿同时存在时，单模型按 3:1 推进且没有并发连接。
2. 终稿处理期间直播 PCM 文件持续增长，直播分片从正确时间范围读取。
3. 下播末尾流失效后实时任务不显示整场失败，并自动生成离线终稿任务。
4. 离线缺失分片自动续接，完整度达到 100% 后才显示“话术完整”。
5. 详情页显示真实覆盖率和语速来源，未知时长显示“待计算”。
6. 后端全量测试、前端类型检查、Lint 和生产构建全部通过。

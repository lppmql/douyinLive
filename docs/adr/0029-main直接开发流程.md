# ADR 0029：main 直接开发流程

日期：2026-07-29

## 背景

项目原本讨论过“主分支为准，临时分支开发，合并后删除临时分支”的方案。这个方案更安全，但实际执行时需要创建分支、处理 worktree、合并、清理分支，对当前维护节奏来说偏麻烦。

用户明确决定：取消分支开发，后续全部在 `main` 里开发。

`main` 的大白话解释：它就是项目唯一主线，像正式营业的店面。所有改动直接在这里做，省掉分支来回切换。

## 备选方案

### 方案 A：临时分支开发，合并后删除

优点：
- `main` 更安全，不容易被半成品污染。
- 每个任务独立，方便回退。

缺点：
- 命令多，流程绕。
- 对编程新手来说，分支、worktree、merge、冲突处理都容易增加负担。

### 方案 B：全部直接在 `main` 开发

优点：
- 最简单，只有一条主线。
- 不需要记分支名，也不需要处理分支清理。
- 更符合当前“一个人维护 + AI 协作”的使用方式。

缺点：
- `main` 更容易被半成品影响。
- 必须更重视提交前测试、审查和 `git status` 检查。

### 方案 C：长期 `main` + `develop`

优点：
- 适合多人团队和正式发布节奏。

缺点：
- 当前项目不需要这么复杂。
- 两条长期分支会增加理解成本。

## 决策

选择 **方案 B：全部直接在 `main` 开发**。

后续默认规则：

1. 日常开发、修复、文档维护都直接在 `main` 上完成。
2. 每次动手前必须先执行 `git status`，确认没有无关脏文件。
3. 如果有历史残留文件，先说明来源并备份，不能混进新提交。
4. 提交前仍必须通过单元测试 Agent 和代码审查 Agent。
5. 每次提交后直接推送 `origin/main`。

## 影响

- `AGENTS.md` 增加“main 直接开发”规则。
- `docs/开发.md` 改为 main 单主线开发流程。
- 之前创建的 `codex/...` 临时分支不再作为日常开发方式，后续可在确认内容已进入 `main` 后清理。

## 风险控制

为了避免 `main` 被半成品污染，保留以下硬要求：

- 不跳过测试。
- 不跳过代码审查。
- 不提交 `.env`、Cookie、Token、浏览器指纹、数据库密码等敏感信息。
- 不把不相关的旧文件残留混入当前提交。

## 验收

- 新任务不再需要创建功能分支。
- 开发文档中的开始步骤只围绕 `main`。
- 提交前仍能看到测试和审查记录。

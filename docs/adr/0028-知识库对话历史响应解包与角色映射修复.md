# ADR 0028 — 知识库对话历史响应解包与角色映射修复

**日期**: 2026-07-29
**状态**: 已实施
**关联**: [ADR 0027 — 知识库 Chat UI 全面升级（方案 C）](./0027-知识库ChatUI全面升级方案C.md)

---

## 背景

2026-07-28 的知识库 Chat UI 升级加入了对话历史接口和侧边栏。回退与合并后检查远端 `main` 发现：

1. 后端测试通过，前端生产构建通过。
2. `pnpm typecheck` 失败，错误集中在 `useConversations.ts`。
3. 新增对话历史代码把 `backendRequest` 的完整响应对象直接当成业务数据使用。
4. 后端历史消息角色使用 `assistant`，前端聊天气泡只识别 `ai`。
5. 新对话创建时先保存首条用户问题，随后追加消息接口又保存同一条用户问题和 AI 回答，导致历史对话里第一条问题重复。

`backendRequest` 的大白话解释：它不是只返回后端数据本身，而是返回一个带 `data`、`error`、`response` 的请求结果。页面要先拿出 `data`，再当成对话列表或对话详情使用。

如果不修复，类型检查会阻断提交；历史对话加载时也可能把响应壳当数组渲染，或把 AI 消息当成用户消息显示。

## 备选方案

### 方案 A：在对话 composable 里按项目现有工具解包（采用）

- 使用已有 `unwrapServiceData` 统一处理 `data` 和 `error`。
- 把后端 `assistant` 映射为前端 `ai`。
- 历史消息补上 `backendMsgId`，让赞/踩反馈能找到后端消息 ID。
- 新对话只先创建空对话标题，问答内容统一通过追加消息接口保存一次。

优点是改动小，复用项目现有请求处理方式，不改变后端接口。

### 方案 B：改 `backendRequest` 的类型定义

优点是可以减少很多页面里的解包代码。缺点是影响全站请求类型，风险比本次问题大。

### 方案 C：让后端返回前端角色名 `ai`

优点是前端少一步转换。缺点是后端已经采用更通用的 `assistant` 角色名，改接口会影响已保存历史数据和未来多端兼容。

## 决策

采用方案 A。

本次只修复知识库对话历史的响应解包和消息映射，不调整 UI 布局、不新增依赖、不改变后端接口。

## 影响

- `pnpm typecheck` 恢复通过。
- 对话列表读取 `response.data` 后再渲染，避免把请求响应壳当数组。
- 历史 AI 消息按 AI 气泡显示，来源仍能被右侧来源面板识别。
- 赞/踩反馈可使用历史消息或新保存消息的真实后端消息 ID。
- 新建对话后，第一条用户问题只保存一次。

## 验收方式

1. `cd frontend && pnpm typecheck` 通过。
2. `cd frontend && pnpm build` 通过。
3. 打开知识库页面，历史对话列表能加载。
4. 点击历史对话后，用户消息和 AI 回答左右气泡正确。
5. 对 AI 回答点赞或点踩，后端收到真实消息 ID。
6. 新建对话并提问后，历史消息里第一条问题不重复。

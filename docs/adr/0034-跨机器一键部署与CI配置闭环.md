# ADR 0034：跨机器一键部署与 CI 配置闭环

日期：2026-08-01

状态：已采纳

## 背景

项目换到新电脑后，一键启动暴露出以下真实问题：

- `dataease/conf/application.yml` 不存在时，Docker 会创建同名目录，导致 DataEase 无法加载配置。
- DataEase、FunASR 等可选重服务失败会阻断前端和后端主系统。
- 端口清理逻辑可能把 Docker Desktop 的端口代理进程当作业务进程结束。
- DataEase 数据库和只读账号没有形成首次部署闭环。
- 全新数据库即使扫码成功，也会在企业后台自动发现直播间前被空 `live_rooms` 校验拦截。
- macOS 进程表可能包含非 UTF-8 字节，ASR 状态查询和关闭流程会解码失败。
- CI 没有安装已经执行的 `ruff`，Docker 检查也没有准备环境文件。

## 备选方案

### 方案 A：继续依赖人工准备配置和服务

优点是改动最少；缺点是每台新机器都要重复排查，无法称为一键部署。

### 方案 B：把所有服务都改成强制启动

优点是功能一次性齐全；缺点是 DataEase 或 FunASR 首次下载、模型加载失败会让主系统完全不可用。

### 方案 C：核心服务强校验，可选重服务安全降级

MySQL、Redis、Qdrant、后端和前端必须健康；DataEase 与 FunASR 使用明确配置和健康检查，但失败时给出原因并允许主系统继续。必要的 DataEase 配置随 Git 保存，运行数据和真实密钥继续忽略。

## 决策

采用方案 C，并做以下约束：

1. `dataease/conf/application.yml` 纳入版本管理，真实密码只通过根目录 `.env` 注入。
2. 一键启动自动等待 MySQL，并幂等创建独立 `dataease` 数据库。
3. DataEase 使用专用只读账号访问业务库，不复用主业务写账号。
4. 端口清理识别 Docker Desktop 进程并拒绝误杀。
5. FunASR 是否自动启动由 `ASR_AUTO_START` 控制；镜像和模型只在首次部署下载。
6. macOS 进程扫描使用 UTF-8 容错解码，不让单个异常字节破坏控制中心。
7. CI 的依赖与执行命令保持一致；Docker 检查从 `.env.example` 创建临时 `.env`。
8. `.env.example` 只面向 `DEBUG=true` 的本机首次运行，允许用户指定的首次密码；`DEBUG=false` 时后端与环境诊断继续强制生产密码长度。
9. 首次采集复用扫码账号的 Cookie 与浏览器指纹，访问企业主播列表并从平台真实重定向 URL 自动取得最近有效 `roomId`；只有平台确实没有任何直播记录时才提示无法发现。

## 影响范围

- 根目录环境变量模板与一键启动脚本。
- Docker Compose 的 DataEase 环境注入。
- DataEase 外部配置和数据库准备流程。
- ASR 本地进程状态检测。
- Qdrant 向量集合初始化。
- GitHub Actions 后端与 Docker 检查。

## 安全边界

- `.env`、API Token、Cookie、浏览器指纹、数据库文件、FunASR 模型和运行日志不得提交。
- `.env.example` 只保留本机首次初始化示例，不得包含线上密钥；示例密码不得用于对外部署。
- 新机器必须根据实际环境修改所有密码与密钥后再用于正式部署。

## 验收方式

1. 全新检出后，复制 `.env.example` 可通过 `docker compose config -q`。
2. 一键启动能够创建 DataEase 数据库并通过登录 RSA 链路检查。
3. DataEase 只读账号仅拥有业务库的 `SELECT` 与 `SHOW VIEW` 权限。
4. FunASR 镜像下载完成后能监听本机 `10096`。
5. 控制中心轮询和按 `Ctrl+C` 关闭不再出现 Unicode 解码错误。
6. 后端测试、ruff、前端类型检查、lint、构建、Alembic 和 Docker 检查全部通过。
7. 空 `live_rooms` 且账号已登录时，首次采集可自动保存平台返回的根直播间并继续企业主播与历史场次同步。

# ADR 0045：历史详情失败重试与回放状态边界

- 日期：2026-08-28
- 状态：已采纳

## 背景与真实证据

场次 #2529 的详情错误为“平台详情页未回显该场次时间，无法安全确认主播归属”。旧实现将其记为 `unavailable`，前端显示“平台不可回放”，后续补齐又跳过该状态。

2026-08-28 使用项目保存的采集号登录态、浏览器指纹重新采集后，回放刷新接口成功，流来源 #4000 为 `active`。随后只读调用原详情采集器，页面回显 `08-28 12:44:14 ~ 08-28 14:04:53`，与数据库一致，返回 52 个汇总指标字段、81 条趋势、45 条评论、36 项画像。最初失败的页面内容没有留存，因此不能断言当时一定是网络慢或某种格式错误。

检查发现 1019 场旧记录具有同样的误分类原因。直接把它们全部重新加入单浏览器采集，会让一次刷新变成大规模历史重采。

## 决策

1. 详情是否采集成功与回放是否可播放分开表达。沿用已有状态字段；`retryable` 显示“详情待重试”，`unavailable` 显示“详情暂不可用”，不再把详情错误当成视频不存在。
2. 保留现有场次时间匹配与防串场保护。页面首次未匹配时，最多额外等待三次、每次一秒；正常匹配不增加等待。仍不匹配则不写入该页的指标、评论、画像或回放。
3. 时间校验失败、详情接口暂时为空均记为 `retryable`。只兼容旧版两个明确误分类错误，不自动恢复未知 `unavailable` 原因。
4. 新场次首次采集不减量；失败重试每次刷新最多 10 场，距离上次更新时间至少 30 分钟，优先最久未尝试的记录，防止同一批失败永远占据队头。未尝试的记录计入剩余数量，不静默丢弃。
5. 使用已有 UTC `updated_at` 作为保守冷却依据，不新增数据库字段。其他操作更新此字段可能延后重试，但不会提前绕过冷却；重复相同错误时也显式更新时间。
6. 内部详情补齐函数支持明确的 `session_ids` 范围，供定点验收；显式范围可立即重试，空集合不退回全量。不新增公开接口，不暴露 Cookie，不修改数据结构或 DataEase 既有入库映射。
7. 不放宽 ASR 的详情完整门槛，不手动启动 ASR 或 AI。真实补齐成功后，如现有自动 ASR 服务开启，由原有“昨天/今天”规则决定后续排队。
8. 大屏回显的省略号/星号名称不作为完整主播资料入库，避免重试时覆盖企业列表已有的真实名称；仍允许补齐真实名称和其他完整资料。

## 取舍

- 不选择“取消时间校验”：拿到视频地址不等于已确认场次归属。
- 不选择“一次恢复全部旧记录”：保持单浏览器并发，限制历史失败带来的额外负载。
- 不选择“新增整套回放状态机和数据库迁移”：本次只修复详情状态语义和失败恢复，回放仍使用已有流来源与探测链路。
- 自动批次仅在后续刷新时推进，不新增定时器；若需补齐指定旧场次，使用明确范围的运维调用。

## 验收

- 回归覆盖：真实页面时间格式、延迟回显、错场拒绝、旧错误兼容、未知错误保留、重试上限/冷却/轮转、定点范围及空范围、失败时保留旧回放。
- 前后端联动按高风险执行一次 `make check`；失败只重跑受影响检查。
- 真实采集验收仅针对 #2529，不把 1019 场历史记录作为本次操作目标。
- 定点补采实测：`checked_count=1`、`enriched_count=1`、`failed_count=0`、`remaining_count=0`，状态为 `complete`、旧错误清空，保存 81 条指标、45 条评论、36 项画像。
- 本次发现平台名称显示为“零食赛道严...-文豪”；依据采集前记录及相同抖音 UID 的相邻场次，恢复“零食赛道严选-文豪”，并增加名称覆盖保护回归。

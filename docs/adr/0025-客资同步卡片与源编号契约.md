# ADR 0025：客资同步卡片与源编号契约

- 日期：2026-07-27
- 状态：已采纳
- 关联方案：A（独立同步服务 + 控制中心卡片）

## 背景

“抖音站内私信客资”原来是采集页里一张独立的大卡片，虽然能手动同步和查看状态，
但与 DataEase 数据库同步分散在不同区域，用户不容易理解两者都是后台数据同步能力。

同时，新部署的客资服务源码位于 `/Users/lpp/kezi`。它的
`GET /api/douyinhao` 文档要求客户端使用 `lastId` 增量拉取，但旧响应没有返回每条记录
自己的数据库编号。主系统无法确认本页数据是否连续，只能拒绝推进游标，避免静默漏数。

## 备选方案

### 方案 A：保留独立定时器，只统一控制中心展示（采用）

- 优点：不改变已经验证过的客资同步、去重和场次归属逻辑，改动范围小。
- 优点：卡片可以紧跟 DataEase，用户能在同一区域查看全部自动同步能力。
- 缺点：客资同步仍不属于统一任务队列，需要使用自己的状态接口。

### 方案 B：把客资同步改造成统一任务队列模块

- 优点：任务暂停、重试和日志入口可以完全统一。
- 缺点：需要迁移定时器、锁和游标状态，容易影响正在运行的真实客资链路。

### 方案 C：合并进 DataEase 同步任务

- 优点：表面上的模块数量更少。
- 缺点：客资来源、失败恢复和隐私边界与报表同步不同，互相捆绑后维护风险更高。

## 决策

采用方案 A：

1. 前端统一使用“客资同步”名称。
2. 客资卡片放进“数据处理控制中心”的同一个网格，固定渲染在后端模块列表之后。
   当前模块列表最后一项是 DataEase，因此页面顺序稳定为“DataEase 数据库同步 → 客资同步”。
3. 卡片继续调用独立的 `/api/douyin/leads/sync-status` 和 `/api/douyin/leads/sync`，
   不伪装成任务队列模块，也不删除原来的手动同步功能。
4. 客资服务的每条 `data` 必须返回正整数 `sourceId`，并且页面中的编号严格递增；
   页面 `lastId` 必须等于最后一条记录的 `sourceId`。
5. 手机号或抖音号任意一个存在都视为有效客资，避免漏掉只留手机号的人。

这里的“接口契约”，大白话就是两个系统事先约定好的数据格式。只要服务端漏掉
`sourceId` 或编号顺序不对，主系统就停止本页同步，不移动游标，从而让问题可以修复和重试。

## 安全与隐私

- `KEZI_API_KEY` 只由后端读取，前端卡片只能看到数量、状态和游标。
- 卡片不显示手机号、抖音号或客户姓名。
- 主系统继续使用“来源 + 源编号”唯一约束去重，不拿联系方式猜测记录身份。
- 场次匹配必须同时满足真实主播名称和直播时间窗；证据不足就保留为“待归属”。

## 验收标准

1. 控制中心中“客资同步”卡片紧跟 DataEase 数据库同步。
2. 立即同步、自动轮询、失败提示、累计数量、待归属数量、重复数量和游标均保留。
3. `/Users/lpp/kezi` 返回项包含 `sourceId`，并包含只有手机号的真实客资。
4. 主项目的类型检查、生产构建、后端测试和真实保存 Cookie/浏览器指纹验收通过。

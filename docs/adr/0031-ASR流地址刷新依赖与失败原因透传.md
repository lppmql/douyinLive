# ADR 0031：ASR 流地址刷新依赖与失败原因透传

- 日期：2026-07-29
- 状态：已采纳

## 背景

直播话术页出现 7 个失败的离线终稿任务。数据库中的任务错误只显示：

> 真实流未输出任何音频帧，请刷新流地址后从断点重试

继续查看 ASR Worker 日志后发现，底层 ffmpeg 实际报错是抖音 CDN 返回 404，说明回放流地址已经失效。系统本来会调用流地址刷新接口自动恢复，但刷新接口又因为本机 Playwright Chromium 缺失而失败。

这导致运营在页面上只能看到“无音频帧”，看不出真正要处理的是“流地址失效 + 浏览器依赖缺失”。

## 备选方案

### 方案 A：只安装缺失的 Playwright Chromium

优点是立刻恢复自动刷新能力，风险低。

缺点是以后如果刷新接口再次失败，页面仍然可能只看到笼统错误。

### 方案 B：只增强失败原因展示

把 ffmpeg stderr 和刷新 API 错误透传到任务失败原因。

优点是排查更快。

缺点是不会修复当前本机依赖缺失，失败任务仍可能继续失败。

### 方案 C：完整降级链路

自动刷新失败后，继续尝试复用用户 Chrome、浏览器指纹或其他流获取方式。

优点是自动恢复能力最强。

缺点是改动面大，需要重新梳理浏览器会话权限和采集链路，不适合这次快速修复。

## 决策

采用方案 A + B。

1. 在本机安装当前 Playwright 版本需要的 Chromium，恢复流地址自动刷新能力。
2. 后端保留 ffmpeg 最近一次 stderr，并在空音频失败时写入分片错误原因。
3. 自动刷新 API 返回错误时，把刷新失败详情拼入“流地址已失效”的任务错误。

这次不做方案 C。后续如果刷新接口仍然频繁失败，再单独设计“复用 Chrome/指纹”的降级方案。

## 影响

- 直播话术页失败任务能看到更具体的失败原因，例如 404、403、浏览器依赖缺失。
- 已经完成的分片不删除，失败任务仍按断点重试逻辑处理。
- FunASR 容器启动逻辑不变。
- 自动刷新流地址仍走原来的后端刷新接口，不新增外部服务。

## 验收方式

1. `backend/.venv/bin/python -m playwright install chromium` 能成功安装 Chromium。
2. Playwright Chromium 可执行文件存在。
3. 单测覆盖“无音频帧 + ffmpeg 404 原因透传”。
4. 后端 pytest、前端 typecheck、前端 build 通过。
5. 直播话术页能打开，失败任务原因不再只有笼统的“无音频帧”。

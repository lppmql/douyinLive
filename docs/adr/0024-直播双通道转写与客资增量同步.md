# ADR 0024：直播双通道转写与客资增量同步

- 日期：2026-07-27
- 状态：已采纳
- 关联方案：A 的安全基础 → B 的业务闭环 → C 的模块治理

## 背景

项目的核心目标是通过零食店开店避坑知识直播，引导用户在抖音站内私信留资。
因此“话术能及时看到”和“私信客资能可靠回到直播场次”必须形成一条真实业务链。

排查真实运行数据后确认了两个根因：

1. 直播中和下播后的转写都发送了 FunASR `offline` 协议，直播任务无法持续产生初稿；
   同时容器使用仅离线启动脚本却配置了实时标点模型，C++ 服务反复退出。
2. 客资服务原有接口没有返回源记录编号，主系统无法可靠去重；查询还只返回有抖音号
   的记录，会漏掉只有手机号的有效留资。

## 备选方案

### 方案一：全部使用离线转写

- 优点：实现简单，最终稿相对稳定。
- 缺点：直播过程中看不到话术，下播前无法观察主播正在讲什么。

### 方案二：全部使用在线转写

- 优点：直播时反馈快。
- 缺点：临时结果容易重复或修正，不能作为下播复盘的最终文本。

### 方案三：直播初稿与下播终稿双通道（采用）

- 直播中使用 `online`，按真实语速发送音频，持续保存 `asr_realtime` 临时稿。
- 下播后创建独立 `offline` 任务，快速处理完整回放并生成最终稿。
- 离线分段先使用页面不可见的暂存类型保存断点；只有最终稿完整入库后，才在同一
  数据库事务里公开终稿并删除临时稿，失败时保留可查看内容。
- 直播初稿只用于直播中观察，不触发评分、AI 复盘、知识库或 DataEase；这些派生产物
  只在离线终稿成功后生成，并覆盖重算可能存在的历史评分。

客资同步同时采用“后台增量拉取”：

- 主系统只在后端保存强密钥，浏览器看不到密钥。
- 客资服务返回稳定的 `sourceId`；主系统用 `external_source + external_id` 唯一索引去重。
- 同步游标写入数据库，重启后从上次成功位置继续。
- 只有主播名称相同且提交时间位于真实直播时间窗内才自动归属。
- 没有充分证据时保留为“待归属”，绝不伪造场次。

## 决策结果

采用方案三，并让 FunASR 以双通道服务启动。实时与离线任务使用不同幂等键，
因此同一场直播可以先有初稿，再有终稿，而不会互相覆盖任务身份。

客资采用独立同步状态表，不占用浏览器采集、ASR 或 DataEase 任务队列。
前端只展示同步运行状态和数量，不在采集控制卡上暴露手机号或抖音号。

## 安全边界

- `KEZI_API_KEY` 只能写入项目根目录 `.env`，长度至少 32 位，不能提交 Git。
- 客资源服务的读取密钥 `API_KEY` 和写入密钥 `WRITE_API_KEY` 必须不同且均至少
  32 位；漏配或弱密钥时拒绝启动，写入方不能用自己的钥匙批量读取客资。
- 数据库地址、用户名、密码和数据库名全部来自 `.env`，源码不提供弱默认账号。
- 密钥使用固定时间比较，降低通过响应时间猜测密钥的风险。
- 错误日志和写入响应不包含手机号、抖音号、主播名或数据库错误详情。
- 外部接口格式不合格时整页不推进游标，防止静默丢数据。

- 真实直播任务 `#354` 已按 `online` 协议产生连贯的临时话术句段。

## 部署要求

`/Users/lpp/Documents/kezi-main` 不是 Git 仓库，因此本次只能修改并验证本地源码。
上线前需要把该目录重新部署到 `https://kezi.lpp6.com`，并同步完成三处配置：

1. 客资服务器 `.env` 的 `API_KEY` 是“只读同步密钥”，至少 32 位。
2. 主项目根目录 `.env` 的 `KEZI_API_KEY` 必须与服务器 `API_KEY` 完全相同。
3. 客资服务器 `.env` 的 `WRITE_API_KEY` 是另一条至少 32 位的“上游写入密钥”；
   真实提交客资的调用方必须在 `POST /api/kezi` 的 `x-api-key` 请求头携带它。

本次提供的两个代码目录里没有真实写入调用方源码，因此无法替它写入密钥。部署新服务
但未同步改造写入方时，写入会按安全设计返回 401，新客资不会入库；必须把服务部署和
写入方请求头改造作为同一次上线操作完成。

主仓库 `deploy/kezi-service/` 的等价变量名是 `KEZI_READ_TOKEN` 和
`KEZI_WRITE_TOKEN`，分别对应上面的读取与写入密钥。

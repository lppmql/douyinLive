# ADR 0040：稳定性数据闭环与可重复部署

- 日期：2026-08-17
- 状态：已采纳
- 关联：ADR 0034、0036、0039

## 背景

真实数据审计发现三个长期问题：采集登录过期会持续制造同类失败任务；历史字幕多数
只有段落估算时间却仍可被误确认；新电脑首次安装、日常启动和可选大服务混在同一
脚本中，导致每次启动都做过多检查。此外，复盘页看不到从原始场次到可复盘、可剪辑
结果的整体缺口，未归属确认客资也没有运营处理入口。

## 备选方案

### 方案 A：继续以页面提示和人工排错为主

变更小，但失败任务、错误字幕和跨机器环境漂移会继续积累，页面无法形成可执行闭环。

### 方案 B：一次性拆微服务和独立任务平台

隔离充分，但会显著增加本机部署、数据库一致性和运维成本，不符合当前单机运营规模。

### 方案 C：在现有模块化单体中补齐状态契约与部署边界（采纳）

保留现有队列和页面，通过结构化失败、认证熔断、字幕发布门禁、素材保留策略、真实
就绪漏斗和首次安装脚本补齐关键边界。

## 最终决策

1. 任务失败新增 `error_code`、`failure_stage`、`is_retryable`。登录过期后账号进入
   `expired`，实时采集停止创建重复失败任务；重新扫码成功后恢复。
2. `segment_estimated` 字幕默认不能确认发布，必须先精确重制或人工校对。统计接口
   明确返回精确/估算数量和发布就绪数。
3. 对 `data/videos/<session_id>/replay.mp4` 执行 14 天、20GB 双阈值统计，默认
   只做容量告警。只有运营确认回放已归档或可可靠恢复后，才显式开启自动清理；活动
   直播和运行中剪辑场次始终受保护，成片与字幕不删除。
4. 复盘页展示采集到复盘/剪辑的真实就绪漏斗。确认客资仍坚持“同主播 60 秒配对”，
   未归属项只能人工选择同主播且落在直播或承接窗口内的真实场次；人工结果不可被
   后续重建覆盖。
5. 统一 AI 复盘成为完整复盘入口，旧评分/优化报告只做兼容展示或显式单项运行。
   低置信度和未知回应只显示为待人工确认候选。
6. `setup.sh` 负责首次安装和大体积下载，`start.sh` 只做快速检查。日常启动提供
   `lite`、`standard`、`full` 三档；固定 Python 3.12、Node 22、pnpm 10.12.4。
7. MySQL root 只用于初始化；FastAPI 和 DataEase 分别使用仅限自身数据库的账号。

## 数据与接口影响

- Alembic 迁移 `c4d5e6f7a8b9` 扩展 `scraper_tasks`。
- 新增复盘就绪漏斗和确认客资待归属/人工归属接口。
- 剪辑候选接口支持远程搜索和指定场次回显，统计接口增加字幕与回放容量指标。

## 验收方式

1. 模拟 Cookie 过期后只产生一次结构化失败，后续周期不再新建失败任务；重新扫码恢复。
2. 估算字幕确认接口返回 409，精确字幕可确认；页面按钮状态一致。
3. 默认回放治理只告警不删除；显式开启后也不触碰成片、字幕、活动场次和运行中任务。
4. 人工归属后重建配对，归属仍保持 `manual`。
5. 新机器只需一次 `./setup.sh`，之后三档启动不自动安装依赖；完整检查通过。

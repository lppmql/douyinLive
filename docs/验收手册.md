# 项目验收手册

本手册集中记录项目关键能力的验收方法。自动化测试可以使用脱敏固定样本，但业务验收必须使用数据库中已经采集到的真实账号、主播和直播场次，不允许为了“通过”补写模拟数据。

## 统一要求

每次验收至少记录日期、操作者、真实账号 ID、真实场次 ID、Git 提交、Trace ID、成功项、失败项和恢复结果。Cookie、Token、浏览器指纹、完整私信内容及 AI 密钥不得写入文档或截图。

常规自检入口：

```bash
make doctor
make test
make lint
make build
```

| 改动范围 | 必跑章节 |
|---|---|
| 登录、Cookie、浏览器指纹、采集、评论、场次补齐 | 数据采集 |
| FunASR、音频分片、直播初稿、离线终稿 | ASR 话术 |
| 场次详情、回放、时间轴、AI 复盘 | 场次复盘 |
| 知识库、行业知识、引用来源、AI 回答 | 知识库 |
| 排班、缺场、无效场次、加场提醒 | 主播排班 |
| 日志、健康检查、监控、DataEase | 可观测性 |
| 客资归属、后台同步 | 数据采集 + 可观测性 |

跨模块改动需要执行所有相关章节。

## 数据采集

前置条件：采集账号已经扫码登录并通过存活检查；MySQL、Redis、前后端正常；选择至少包含两个主播、两个真实 `roomId` 的账号。

1. 记录刷新前主播数、场次数、评论数和最新场次时间。
2. 执行“刷新数据采集”，保存任务 ID 与 Trace ID。
3. 再次刷新，确认相同 `roomId` 不产生重复场次。
4. 启停实时监控，确认开播识别和浏览器上下文恢复正常。
5. 抽查两个主播的最近场次，核对评论 `session_id`、平台时间和场次时间。

通过标准：只保存平台真实数据；重复采集保持幂等；页面数量与日志可追踪；浏览器异常后可复用 Cookie、StorageState 和指纹恢复。登录过期时重新扫码并先检查存活；发生页面关闭错误时排除重复进程后重试；发现评论串场时先停止下游同步并核对映射。

## ASR 话术

前置条件：选择一场真实、已结束、有声且不少于 45 分钟的场次；FunASR 正常；场次存在可用 m3u8 地址。

1. 创建转写任务并记录任务 ID、场次 ID 和 Trace ID。
2. 至少完成两个分片后重启 ASR Worker。
3. 确认成功分片保留，未完成分片继续执行。
4. 核对分片时间、全文、覆盖时长和最终状态。
5. 再次重试同一场次，确认不会删除成功分片。

通过标准：重任务按策略调度；重启后只续跑未完成部分；长场次全文可完整保存；无音频、地址过期和引擎不可用均显示真实原因，不生成模拟话术。地址过期先刷新，FunASR 异常先恢复健康，数据库断开恢复后再重试。

## 场次复盘

前置条件：选择一场同时具有回放、分钟指标、评论和 ASR 话术的真实场次。

1. 进入详情，检查竖屏回放和统一复盘分析。
2. 在时间轴筛选告警、复盘发现、评论、话术和指标。
3. 点击证据，确认播放器跳到对应时间。
4. 切换分钟曲线和 AI 分析，确认没有重复趋势入口。
5. 更新复盘发现状态并刷新确认持久化。
6. 与同主播上一场进行真实跨场对比。

通过标准：结论可追溯到真实证据；缺失数据明确显示；复盘状态可维护；历史整改数据不被删除。回放异常检查转码与缓存；AI 结构异常保留 Trace ID 和上一份报告；无对应时间的证据标记待复核。

## 知识库

前置条件：至少两位真实主播已完成话术、评论、分钟指标和复盘同步；AI 配置可用。

1. 等待后台同步并记录新增、更新、跳过和失败数量。
2. 提问指定主播、场次或日期的问题。
3. 核对引用的场次 ID、时间片和原始证据。
4. 连续追问后切换主播，确认新范围覆盖旧上下文。
5. 从引用跳转场次详情，核对时间和内容。

通过标准：回答只基于真实知识切片；重复同步幂等；明确的新范围优先；数据不足时直接说明。AI 超时保留对话和来源；来源为空先检查 ASR 与知识同步；上下文串主播时清空范围后回归测试。

## 主播排班

前置条件：MySQL 已导入当前真实排班模板，查询范围内存在真实场次。

1. 查询单日、近 7 天和自定义日期。
2. 核对各主播计划场次数。
3. 抽查不足 45 分钟、45～79 分钟、达到 80 分钟和加场场次。
4. 核对开播时间与计划自然小时，检查跨整点提醒。
5. 从缺场、无效、时长不足或加场提醒进入真实场次。

通过标准：一个场次只匹配一个班次；直播中不提前判无效；加场正确汇总；未来班次不提前报缺场。匹配失败时检查主播别名和模板，不猜测映射；规则变化先更新规则来源，不直接修改历史场次。

## 可观测性

前置条件：使用 `./start.sh` 启动全栈，MySQL、Redis、后端及监控服务正常。

1. 请求 `/health`，检查数据库、Redis、监控和配置状态。
2. 请求 API，确认响应头包含 `X-Trace-ID`。
3. 请求 `/metrics`，确认 HTTP、任务、AI 和运行时指标可读。
4. 执行真实知识库问答，确认 `ai_call_traces` 只记录脱敏元数据。
5. 验证 Prometheus 配置和告警规则。
6. 触发可恢复失败，确认任务与日志使用同一 Trace ID。
7. 运行 `make doctor` 检查依赖、容器、浏览器、磁盘与配置。

通过标准：错误可端到端追踪；健康接口不泄密；错误配置会阻断启动；Prometheus、Grafana 和 DataEase 健康状态准确；AI 观测失败不改变模型调用结果。健康降级时按组件排查；Worker 无心跳时只恢复可续跑任务；磁盘不足先清缓存和日志。
